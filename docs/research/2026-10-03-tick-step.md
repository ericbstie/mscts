# What a frozen world runs, and how a client knows a step has ended — 2026-10-03

Evidence for #23, tick-exact Groups. Facts are **verified** with
`scripts/research/javap.py` on the 26.3 server jar unless a line says *inferred*.

## The tick, in order

- `MinecraftServer.processPacketsAndTick` drains `PacketProcessor.processQueuedPackets`
  first, then calls `tickServer` (ADR-0010, #115 amendment).
- `tickServer` counts `tickCount` up on every tick, frozen or not, then calls
  `ServerTickRateManager.tick()`, then `tickChildren`, which ticks each level and the
  connections.
- Chat commands are not run there: they are server tasks, run between ticks in
  `waitUntilNextTick` (ADR-0010, #17 amendment).

## What freezes

- `TickRateManager.tick()` sets `runGameElements = !isFrozen || frozenTicksToRun > 0`,
  then, if `frozenTicksToRun > 0`, takes one off it. It sends nothing.
- `runsNormally()` returns `runGameElements`. `ServerLevel.tick` checks it before the
  world border and the weather (`advanceWeatherCycle`), the time (`tickTime`), the
  block and fluid ticks (`LevelTicks.tick` with `getGameTime()`), and the block events
  (`runBlockEvents`). Scheduled ticks are due by game time, which only a running tick
  advances.
- `isEntityFrozen(entity)` is true when the world does not run normally, unless the
  entity is a `Player` or carries one. Players keep ticking while frozen.
- `ServerLevel.tick` calls `ServerChunkCache.tick` on every tick, frozen or not, after
  the block and fluid ticks and before the block events and the entities. So what a
  stepped tick's block ticks change goes out in that tick, and what its block events,
  entities and block entities change goes out in the next tick, a frozen one.
- Live (the gameplay survey, 2026-09-30): rain set while frozen sends nothing until
  `tick unfreeze`.

## What a step sends

- `ServerTickRateManager.stepGameIfPaused(n)` returns false unless the world is frozen.
  Otherwise it sets `frozenTicksToRun = n` and calls `updateStepTicks`, which sends
  `ticking_step` to every player (`PlayerList.broadcastAll`).
- `updateStepTicks` is called only from `stepGameIfPaused` and `stopStepping`. The
  countdown in `TickRateManager.tick()` sends nothing, so **no packet says a step has
  ended**. Waiting for `ticking_step` at 0 (the issue's first candidate) cannot work.
- `setFrozen` calls `updateStateToClients`, which sends `ticking_state` to every player,
  in the command's task, before anything the next command says.

## The step barrier

mscts steps one tick at a time: `tick step 1` through Control, which waits for its
marker's answer and then passes the barrier (`Bot.sync`).

1. The `tick step 1` task runs between tick T and tick T+1, and the marker's task after
   it, so the marker's answer means `frozenTicksToRun` is 1.
2. Tick T+1 runs normally and sends what changed. Tick T+2 is frozen again.
3. The barrier's first answer comes from a packet pass at T+1 or later. Its second
   request goes out at least `TICK_GAP_S` after that answer arrived, so it is answered in
   a later pass, after T+1 has sent its changes.
4. Then every Bot in play passes the barrier, as at a window's close. Each Bot's first
   request reaches the server after Control's barrier has ended, so its second answer
   comes after tick T+2's packets too, which carry the block events and entity changes
   of tick T+1.

Polling `time query gametime` (the second candidate) would also work, but it needs a
command and its answer per poll, and tells no more than the barrier. The world age in
`set_time` (the third) arrives every 20 ticks only.
