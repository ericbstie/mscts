# How hoppers move items, and when an open container shows it — 2026-10-24

Evidence for #41, the hopper Groups in `redstone`. Facts are **verified** with
`scripts/research/javap.py` on the 26.3 server jar unless a line says *live*.

## The cooldown

- `HopperBlockEntity`: `MOVE_ITEM_SPEED` is 8, `HOPPER_CONTAINER_SIZE` 5, and a new hopper's
  `cooldownTime` is -1 (`NO_COOLDOWN_TIME`). `loadAdditional` reads `TransferCooldown` (default
  -1), so a hopper made by `/setblock` with items and no `TransferCooldown` can move on the first
  tick it runs.
- `pushItemsTick` takes 1 off `cooldownTime` and records the game time (`tickedGameTime`). If
  the hopper is then not on cooldown (`cooldownTime <= 0`), it sets the cooldown to 0 and calls
  `tryMoveItems`.
- `tryMoveItems` does nothing unless the hopper is off cooldown and its state is `enabled`. It
  pushes first (`ejectItems`, if the hopper holds anything), then pulls (`suckInItems`, if the
  hopper is not full). If either moved an item, it sets the cooldown to 8 and marks the block
  entity changed. If neither did, it sets no cooldown, so a hopper whose target is full tries
  again every tick.
- So a hopper that moves on tick N moves next on N + 8 at the earliest.
- `tryMoveInItem` gives a hopper that was empty and is filled by another container a cooldown
  of 8, or 7 if the hopper being filled has already ticked this game tick (its `tickedGameTime`
  is not behind the source's), unless it is on a cooldown above 8 already. The 7 applies only
  when the source is a hopper too.
- `Level.tickBlockEntities` ticks block entities in the order their tickers were added, and only
  when the world runs normally (`TickRateManager.runsNormally`). In a frozen world hoppers move
  only on the ticks `/tick step` runs.

## Push and pull

- `ejectItems` finds the container the hopper faces. If every slot of it, seen from that side,
  holds a full stack (`isFullContainer`: count at least the stack's max size), it moves nothing.
  Otherwise it takes 1 item from the first non-empty hopper slot (0 to 4) and tries to add it;
  if that fails, it puts the item back and tries the next slot.
- Adding to a plain container (`addItem` with no face) tries its slots in index order: an empty
  slot takes the item, a slot holding the same item and components below its max size takes it
  too.
- So a full chest with one slot of 63 stone takes stone from a hopper but not dirt: the hopper
  skips its dirt slot and moves nothing while it holds only dirt.
- `suckInItems` looks at the block above. If it is a container, it tries that container's slots
  in order (the slots seen from below), taking 1 item from the first slot it can.

## Pickup

- With no container above, `suckInItems` checks whether the block above blocks it: the hopper is
  grid-aligned (a block, not a minecart), the block above has a full-block collision shape, and
  is not in `#does_not_block_hoppers`. If it does not block, the hopper takes item entities that
  are alive and whose box meets `Hopper.SUCK_AABB` moved to the hopper.
- `SUCK_AABB` is `Block.column(16, 11, 32)`: the whole block width, from 11/16 of the hopper's
  block up to 2 blocks above its base. `AABB.intersects` is strict, so an item lying on a full
  block above the hopper (its base at y + 2) is not taken, and the block above blocks pickup
  anyway.
- A bottom slab above the hopper does not block: it is not a full block. An item lying on it
  (its base at y + 1.5) is in the box and is taken.
- Taking an item entity copies its whole stack into the hopper's slots in order. If it all fits,
  the entity's item is emptied and the entity discarded; otherwise the entity keeps the rest.
  Taking it counts as a move: the hopper goes on cooldown for 8 ticks.
- `HopperBlock.entityInside` calls `HopperBlockEntity.entityInside`, which calls `tryMoveItems`
  with the item as the only thing to pull when an item entity's box meets the suck box. It does
  not check the block above. It runs in the item's own tick, in the entities' part of a tick,
  before the block entities' part; a stepped tick runs both.
- `ItemEntity.tick` checks the blocks its box is in (`applyEffectsFromBlocks`) on every tick it
  is not on the ground, so every tick for an item with `NoGravity`. A hopper keeps the default
  inside shape, the whole block (`BlockBehaviour.getEntityInsideCollisionShape`), so any item
  whose box is in the hopper's block space reaches `entityInside`. The bowl is the hollow of the
  hopper's shape from 11/16 up, so an item there is in the suck box and collides with nothing.
- So an item in a hopper's bowl is taken in its own tick whenever the hopper is off cooldown,
  even under a full block. Under one, an item that waits out the hopper's cooldown is taken a
  tick late: the cooldown reaches 0 in the hopper's part of tick N, where `suckInItems` takes
  nothing through the block and sets no cooldown, and the item's own tick on N + 1 takes it.
  With nothing above, the hopper takes it on N.
- An item whose box is above the hopper's block space never reaches `entityInside`, so it is
  taken only in the hopper's tick. `NoGravity` keeps a summoned item there: without it, a
  stepped tick drops the item into the bowl.
- An item inside a full block is pushed out (`ItemEntity.tick`: `moveTowardsClosestSpace`) at a
  random speed. So under a full block, no item can be in the suck box without being in the
  bowl, and the block's check shows only in the tick late.

## The lock

- `HopperBlock.checkPoweredState`: the hopper is `enabled` unless it has a neighbour signal.
  If that differs from its state, it sets the new state (flags 2). It runs from `onPlace` and
  `neighborChanged`; a hopper schedules no block ticks.
- So a redstone block placed beside a hopper locks it at once, and removing it unlocks it at
  once. A locked hopper's `tryMoveItems` does nothing, but `pushItemsTick` still counts its
  cooldown down.

## When an open container sends a slot

- `ServerLevel.tick` runs `tickTime` and block and fluid ticks (only when the world runs
  normally), `ServerChunkCache.tick`, block events (only when it runs normally), the entities,
  then `tickBlockEntities`.
- `TickRateManager.isEntityFrozen` is true for an entity that is not a player and carries no
  player, when the world does not run normally. Players tick on every tick, frozen or not.
- `ServerPlayer.tick` calls `containerMenu.broadcastChanges()`. That walks the menu's slots in
  index order and sends `container_set_slot` for each whose `RemoteSlot` no longer matches, so a
  slot that changes and changes back within one tick sends nothing.
- `MinecraftServer.tickChildren` holds every connection's flush at the start of the tick and
  flushes once at the end.
- So a hopper that moves on stepped tick N changes its containers after the players ticked on
  N. The open menu's `container_set_slot` is built in the player's tick of the next server tick,
  N + 1, which the frozen world runs 50 ms later without stepping, and leaves at the end of it.
  A block change is sent one server tick sooner, at the end of N. Both land within the step of
  tick N, before its barrier ends.
- The step barrier still holds it, with no pass to spare. Control's tellraw marker is a chat
  command, so a server task, and can run in the same gap between ticks as `tick step 1`.
  Control's 3 requests are then handled at the passes of N, N + 1 and N + 2 at the earliest. So
  a Bot's first barrier request is handled at the pass of N + 2 or later, the first pass after
  N + 1's flush, and its Mark, after its third answer, comes at N + 4 or later. Something a
  Group needs that is sent at N + 2 or later can race the barrier.
- *live* (`scripts/research/hopper_slot.py`, one vanilla 26.3 Instance, 20 plays idle and 20
  under `--stress 4`): a hopper facing into a chest the watcher has open moved its stone on the
  first step, and the chest's slot landed within that step, before the `tick:1` Mark, in 40 of
  40 plays. It arrived 97 to 108 ms
  after Control sent `tick step 1`, 44 to 54 ms before the watcher's first barrier request, and
  192 to 204 ms before the watcher's `tick:1` Mark.
- *live* (one play of `redstone/hopper-transfer` on vanilla 26.3): every slot change landed in
  the step of the tick its hopper moved on. The upper hopper moved items on ticks 1, 9, 17 and
  25, and the lower one pushed on ticks 8, 16, 24 and 32. On tick 17 the upper hopper's menu
  sent nothing for its slot 0, which gave up one log and took another.

## Opening a chest, and clearing it

- `ContainerOpenersCounter`: the first opener schedules a block tick 5 ticks on
  (`scheduleRecheck`). `recheckOpeners` always calls `openerCountChanged`, which sends a
  `block_event`, and schedules again while anyone has the chest open. So an open chest has a
  block tick due every 5 stepped ticks, and after it is closed one more is still pending. A Group
  that compares `block_event` around an open chest sees these; a Group that clears the chest
  steps 5 ticks first so none is left.
- A hopper's menu (`HopperBlock.useWithoutItem`) is a `HopperMenu` of type `minecraft:hopper`,
  5 slots, and has no openers counter.
- `/fill` and `/setblock` set blocks with flag 256, so `LevelChunk.setBlockState` skips the
  block entity's `preRemoveSideEffects`: a chest or hopper cleared by a command drops nothing.
