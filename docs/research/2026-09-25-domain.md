# Domain research — 2026-09-25

Facts gathered before any product code was written. Everything marked
**verified** was observed first-hand against a running server in this
container; the rest is cited. Re-verify before relying on anything older
than the pinned Target.

## Target

- Latest release **26.3** (2026-09-15), `protocol_version` **777**,
  `world_version` 5023, **Java 25** (`java-runtime-epsilon`). Taken from
  `version.json` inside the server jar. **verified**
- The 26.x server jars ship **without obfuscation mappings** (no
  `server_mappings` download). 1.21.11 still had them.
- The server jar is a bundler (`net/minecraft/bundler/Main`). On first run
  it unpacks its libraries into `libraries/` and `versions/` under the cwd.

## Connection sequence (26.3, offline mode) — verified

Observed from a raw-socket probe client against vanilla 26.3:

1. **Handshake** `minecraft:intention`: protocol VarInt, host String, port
   UShort, next-state VarInt (1 = status, 2 = login).
2. **Status**: `status_request` → `status_response` (a JSON string whose
   `version.protocol` is 777). Localhost round trip was about 6 ms warm and
   70–95 ms on the first connection.
3. **Login**: client `hello` (name String, UUID) → server
   `login_compression` (threshold 256) → `login_finished` → client
   `login_acknowledged`. Offline vanilla sends **no** encryption request.
4. **Configuration**: server sends `custom_payload` (brand),
   `update_enabled_features`, `select_known_packs`. The client echoes
   `select_known_packs`. Then 32 × `registry_data`, which is small
   (≈0.2–1.6 KB) because the known packs matched and the entries carry no
   NBT. Then `update_tags` (≈59 KB) and `finish_configuration`. The client
   acks with `finish_configuration`.
   `code_of_conduct` exists but is off by default
   (`enable-code-of-conduct=false`).
5. **Play**: `login`, then difficulty, abilities, recipes, `commands`,
   `player_position` (teleport id 1 at 6.5, -60, 7.5 on a flat world),
   player info, border, time, spawn position, `game_event`,
   `ticking_state`/`ticking_step`, `set_chunk_cache_center`, inventory,
   entity data, attributes, advancements, health, XP. Chunks arrive in a
   `chunk_batch_start` … `level_chunk_with_light` × N …
   `chunk_batch_finished` bracket. Further batches need the client to send
   `chunk_batch_received`.
6. **26.3 change**: serverbound `accept_teleportation` is now
   `Teleport ID VarInt, X/Y/Z Double, Yaw/Pitch Float`. It echoes the
   resulting pose. Sending only the VarInt gets the client disconnected
   with a decode error.
7. **Keep alive**: vanilla sends one about every 15 s. The client must echo
   the Long. Nothing arrived within the first 8 s of play.
8. **Player Loaded**: vanilla assumes the client has loaded after 60 ticks
   if it never sends the packet.
9. **Wire format**: frames are `VarInt length ‖ payload`. After
   `login_compression` the payload becomes `VarInt data-length ‖ zlib(data)`,
   with data-length 0 meaning "uncompressed". `data` is `VarInt packet-id ‖
   fields`. The disconnect reason in play is an anonymous NBT text
   component.

## Vanilla quirks that affect testing — verified

- **`white-list=true` is the default** in 26.3. A fresh server kicks any
  client with `multiplayer.disconnect.not_whitelisted`.
- **`pause-when-empty-seconds=60` is the default.** The server stops
  ticking while no players are online, which skews tick timing and world
  state between Scenarios.
- Offline login needs `online-mode=false`. Also consider
  `enforce-secure-profile=false` for unsigned chat.
- Flat world: `level-type=minecraft\:flat`, `generate-structures=false`.
- Cold start to `Done` is about 0.4 s of server time on the second boot
  (world exists) and a few seconds on the first boot (library unpack +
  worldgen). The data generator takes about 5 s.
- The JSON-RPC **management server** (`management-server-*`, off by
  default) lets you administer allowlist, ops, settings, kick, save and
  stop over WebSocket. It is vanilla-only.

## Vanilla 26.3 config files — verified

Observed against the 26.3 jar (sha1 `33680f5f…`) with Temurin 25.0.4.1.

- **Default set.** A first run in an empty directory, with no EULA
  accepted, writes the defaults to `server.properties` and `eula.txt`, then
  exits after about 2 s. The file has **69 keys**, sorted, and
  `VanillaAdapter` pins every one of them. Re-run this after any Target bump
  to catch new or renamed keys.
- A missing `management-server-secret` gets a random 40-character value. An
  explicitly empty one stays empty.
- Vanilla reads `server.properties` as UTF-8, falling back to ISO-8859-1,
  and **rewrites it on every start**. Given the file that
  `VanillaAdapter.prepare` writes, its rewrite was byte-identical apart from
  the date comment. So every value and escape round-trips.
- `level-type=minecraft\:flat` with `generator-settings={}`, vanilla's own
  default, logs `ERROR: No key layers in MapLike[{}]` and falls back to the
  classic flat preset. Spawn is at y = -60.
- **Vanilla calls Mojang services even in offline mode** (authlib 10.0.77).
  At startup it fetches `https://discovery.minecraftservices.com/minecraft/client`
  and the public keys. The console `op <name>` looks names up through the
  profiles API. `VanillaAdapter` now cuts this off; see
  [the next section](#vanilla-263-makes-no-outbound-connection--verified).
- With services unavailable, the console `op Steve` wrote
  `{"name": "steve", "uuid": "53909932-…"}`, the offline UUID of the
  **lower-cased** name. A Bot that logs in as `Steve` gets `5627dd98-…`
  instead, so it would not be op. Write `ops.json` directly; never op through
  the console.
- A first start creates `banned-ips.json`, `banned-players.json`,
  `whitelist.json` and `usercache.json`, each `[]` or a small list. It took
  about 12 s to `Done` on first boot in this container, and an offline probe
  login reached play and chunks.
- `ops.json` is Gson pretty-printed: 2-space indent, no trailing newline,
  with entry keys `uuid`, `name`, `level` and `bypassesPlayerLimit`. That is
  byte-for-byte `json.dumps(entries, indent=2)`. With the `ops.json` that
  `VanillaAdapter.prepare` writes, a Bot logging in offline as the mixed-case
  `Mscts_Op` joined at op level 4 (play `entity_event` status 28, which is
  24 + level). Vanilla left the file byte-identical.
- For the default ServerSpec, the status response was
  `{"description": "mscts", "players": {"max": 20, "online": 0}, "version": {"name": "26.3", "protocol": 777}}`.
  The first `player_position` was at (4.5, -60, -1.5) with seed 0. Session 1
  saw (6.5, -60, 7.5) with a random seed. The join position **does** vary
  between runs with the same seed (see the side observation below), which
  matters for the M4 Masks.
- The offline UUID is Java `UUID.nameUUIDFromBytes(("OfflinePlayer:" + name).getBytes(UTF_8))`,
  an MD5 version-3 UUID: `Notch` → `b50ad385-829d-3141-a216-7e7d7539ba7f`
  (jshell).

## Vanilla 26.3 makes no outbound connection — verified

Observed against the 26.3 jar with Temurin 25.0.4.1, launched from a
`VanillaAdapter.prepare` LaunchPlan (env `PATH` only) under
`strace -f -e trace=connect,sendto,sendmsg,sendmmsg,bind,openat`.

**Where the calls come from** (read from the class files in `libraries/`
with `javap -c -constants`):

- `net.minecraft.server.Main` always calls
  `MinecraftServicesDiscoveryService.create(Proxy.NO_PROXY)`, whatever
  `online-mode` says. So no `http(s).proxy*` setting applies.
- authlib 10.0.77 takes **every** Mojang service URL (public keys, profile
  and name lookups, session, textures) from one discovery document. Its
  URL comes from `EnvironmentParser`: `minecraft.api.env` (`prod` or
  `staging`) wins if set, otherwise `minecraft.api.discovery.host`, which
  is used as the **whole URL** (not a host). Otherwise the default is
  `https://discovery.minecraftservices.com/minecraft/client`. These are the
  only `minecraft.api.*` properties in authlib, the server jar and every
  bundled library. The older per-service `minecraft.api.*.host` properties
  are gone.
- The fetch runs on the "Minecraft Services Discovery" thread
  (`RetryableFetch`). Any `Exception` counts as "offline": every later
  lookup fails at once with "Services are unavailable", and the fetch is
  retried after 5 × 2ⁿ minutes (n ≤ 6). A malformed URL would throw an
  `Error` there instead, so the future would never complete. The URL must
  be well-formed.
- log4j-core 2.26.0 resolves the local host name at startup
  (`LoggerContext.setConfiguration` → `NetUtils.getLocalHostname` →
  `InetAddress.getLocalHost`). That goes through the OS resolver: here
  `uname`, nscd, `/etc/host.conf`, `/etc/resolv.conf`, `/etc/hosts`. It
  only stayed local because this container's hostname (`vm`) is in
  `/etc/hosts`. On other hosts it becomes a DNS query.
- Other network code (text filtering through msal4j, including the
  `169.254.169.254` IMDS address, the query and RCON listeners, JMX, and the
  management server) is off under the pinned `server.properties`.

**Before** (current `main`): a DNS query to `8.8.8.8:53`, then TCP to
`150.171.110.195:443` (discovery). That failed here only because the
container's TLS proxy is not in the JVM's trust store (PKIX). On a host with
direct internet it would succeed, and the Reference would then have Mojang's
public keys and real name lookups.

**After**, with `-Dminecraft.api.discovery.host=http://127.0.0.1:0/
-Djdk.net.hosts.file=/dev/null` (`VanillaAdapter.NO_NETWORK`):

- The only `AF_INET` connect is to `127.0.0.1:0`, which is refused at once.
  Nothing can listen on port 0, because binding port 0 picks an ephemeral
  port. The log shows `Environment[discoveryUrl=http://127.0.0.1:0/,
  name=properties]`, then "Failed to connect … Connection refused" about
  0.1 s later.
- There is no DNS: `/etc/hosts`, `/etc/resolv.conf` and `/etc/host.conf`
  are never opened. `jdk.net.hosts.file` makes the JDK resolve names from
  that file only (here `/dev/null`, so every name is unknown and no query
  is ever sent). The log4j lookup reads `/dev/null` and falls back.
- What remains is harmless: the `bind` of the game port on `127.0.0.1`, an
  nscd `AF_UNIX` probe at JVM start (the passwd lookup for `user.home`,
  then `/etc/passwd`), and Netty's feature probe `sendmmsg(-1, NULL, 0, 0)`
  (`isSupportingSendmmsg`, fd -1, `EBADF`), which sends nothing.
- A status ping, an offline login to play with 9 chunks, op level 4 from
  `ops.json` (`entity_event` 28) and console `op` all behaved exactly as
  before. Console `op Steve` still fails its name lookup ("Services are
  unavailable") and ops the lower-cased `steve`.
- Startup time did not change here. Launch to the first status ping
  answering 777 took 9.9 / 10.2 / 10.1 s before and 10.2 / 9.9 / 10.3 s
  after, in alternating runs with a fresh workdir each time. That is
  expected, because the old calls also failed fast here. On a host whose
  DNS is slow or unreachable, the old launch would have waited for the
  resolver's timeouts (inferred, not observed).
- **Side observation**: the first `player_position` of a fresh flat world
  with seed 0 was (-2.5, -60, -6.5), (-3.5, -60, -4.5) and (5.5, -60, 1.5)
  in three runs here. Worker B saw (4.5, -60, -1.5). So the join position **does vary
  between runs** with the same seed (vanilla's spawn radius). M4 needs a
  Mask or a pinned spawn for it.

### Pumpkin nightly (0.2.0+26.3) — verified

- Config lives in `pumpkin.toml` (created on first run) plus `data/*.json`
  (ops, bans, whitelist).
- Defaults that break a test harness: `[networking.bedrock] enabled = true`
  (fails to bind UDP 19132 here, "Address family not supported"),
  `[networking.java] online_mode = true`, `encryption = true`, and
  `[telemetry] enabled = true` (phones home).
- **With `online_mode = false` but `encryption = true` it still sends an
  encryption request** (`login/hello`). Vanilla offline never does. The
  Adapter must set `encryption = false`.
- Status JSON differs from vanilla: it adds `players.sample: []` and a
  favicon, and `description` is an object rather than a string.
- The join sequence reached play but diverged:
  - it sends an extra `server_links`;
  - `registry_data` is ≈172 KB (full NBT despite the known-packs match);
  - `set_time` is 19 B where vanilla's is 31 B;
  - no `player_position` or chunks arrived within 8 s on its default
    (non-flat) world.

  These are examples of what the diff engine must surface. They are not
  yet confirmed as bugs.
- It **ignores `--version`**: it just boots a server in the cwd and writes
  `pumpkin.toml`, `data/`, `logs/` and `world/` there. Only run it inside a
  scratch workdir.
- It has a `pumpkin-gametest` crate (a GameTest-style runner). That is
  internal, not a server-agnostic interface.

## Implications for the design

- The only interface common to every candidate is the wire protocol at one
  protocol version. Config formats, consoles and admin APIs differ per
  server.
- Readiness should be detected in a server-agnostic way: poll the status
  ping until it answers with the expected protocol. Do not parse logs.
- Every Adapter must write the **complete** config explicitly and never
  rely on defaults. Defaults change between versions (whitelist) and
  between servers (encryption, telemetry).
- Packet IDs must come from the generated report for the pinned Target.
  Field layouts must be checked against vanilla in a reference-tier test
  before they are trusted.
