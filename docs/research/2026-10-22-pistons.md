# How pistons push, pull and power up, tick by tick — 2026-10-22

Evidence for #40, the piston Groups in `redstone`. Facts are **verified** with
`scripts/research/javap.py` on the 26.3 server jar unless a line says *live*. The client runs
the same `PistonBaseBlock.triggerEvent` when it reads a `block_event`, and moves its own copy of
the blocks; it skips the server's signal check (`isClientSide`).

## When a piston acts

- `PistonBaseBlock.checkIfExtend` runs from `neighborChanged`, from `setPlacedBy`, and from
  `onPlace` when the block before was another block and there is no block entity. A powered
  piston that is not extended queues a block event of type 0 (`Level.blockEvent`, data: its
  facing's 3D value) only when `PistonStructureResolver.resolve` succeeds. A push that cannot
  resolve queues nothing, so the client is sent nothing.
- An extended piston that has lost its power queues type 1, or type 2 when the block 2 ahead is
  a `moving_piston` facing the same way whose `PistonMovingBlockEntity` is extending and either
  its progress is below 0.5, or the game time equals its `lastTicked`, or the level is handling
  its tick (`ServerLevel.isHandlingTick`).
- `ServerLevel.tick` runs, in order: `tickTime` (only when the world runs normally, so a frozen
  world's game time moves only on the ticks it steps), block ticks, fluid ticks, raids,
  `ServerChunkCache.tick`, `runBlockEvents` (again only when it runs normally), the entities,
  then `tickBlockEntities`.
- `PistonBaseBlock.triggerEvent` checks the signal again. Type 0 calls `moveBlocks`; if that
  fails, the event is dropped. Otherwise the piston becomes `extended=true` (flags 67) and plays
  `PISTON_EXTEND` at volume 0.5, pitch `nextFloat() * 0.25 + 0.6`.
- Type 1 or 2 finishes the head's moving block entity if there is one, turns the piston into a
  `moving_piston` (flags 276) holding the retracted piston, and plays `PISTON_CONTRACT` at volume
  0.5, pitch `nextFloat() * 0.15 + 0.6`. A plain piston then removes its head. A sticky one looks
  at the block 2 ahead. If that is a `moving_piston` still extending the same way, it finishes it
  at once, which puts the block down where it was pushed. Otherwise, on type 1 only, it pulls the
  block back with `moveBlocks` if the block is pushable and `PushReaction.PUSH_PULL`, or is a
  piston. Anything else, and type 2, leaves the block and removes the head.
- `PistonMovingBlockEntity.tick` sets `lastTicked` to the game time, then: if the progress was
  already 1, it removes itself and puts the moved block down (flags 67, then `neighborChanged`);
  otherwise it adds 0.5. A block event that runs on tick N makes the moving blocks, which tick
  the same tick (block entities tick after block events): 0.5 after tick N, 1 after N + 1, and
  the blocks are down on N + 2.
- `PistonMovingBlockEntity` has `getUpdateTag` but no `getUpdatePacket`: a moving block sends no
  `block_entity_data`; the client makes its own from the block event.
- So a sticky piston powered for one stepped tick by `/setblock` between the steps drops its
  block: when the power goes, its block has progress 0.5 and was ticked at the game time the
  command sees. The piston retracts with type 2 and finishes the block where it was pushed.

## What a piston can move

- `PistonStructureResolver` moves at most 12 blocks: `addBlockLine` fails once a 13th would be
  added (`1 + toPush.size() > 12`, and `toPush.size() >= 12` before adding).
- `resolve` fails at once if the block in front is not pushable, unless the piston extends and
  the block's push reaction is `POPPED`: then the block is destroyed (`toDestroy`).
- `PistonBaseBlock.isPushable`: air moves; a piston or sticky piston that is extended does not;
  a block whose destroy speed is -1 (bedrock) does not; then by push reaction (`IMMOVEABLE` does
  not); and any other block moves only if it has no block entity (a chest does not).
- `Blocks`: obsidian is `PushReaction.IMMOVEABLE`; a torch is `POPPED`.
- `moveBlocks`: each destroyed block drops its items (`Block.dropResources`) and becomes air
  (flags 18). The break particles (world event 2001) are played on the client only. Each moved
  block becomes a `moving_piston` (flags 324) with a block entity; so does the head's place.
  The places left empty become air (flags 82), in the order of a `HashMap` of their positions.
- `canStickToEachOther`: a honey block and a slime block never stick, either way round; any other
  pair sticks if one of them is slime or honey (`isSticky`). A slime or honey block pulls every
  neighbour that sticks, below it too: one on the grass would drag the grass.

## Quasi-connectivity

- `PistonBaseBlock.getNeighborSignal` is true if any neighbour but the one in front powers the
  piston, or if the piston's own place has a signal downward, or if any neighbour of the block
  above, but the piston, powers that block. So a redstone block 2 above a piston powers it.
- `/setblock` updates only the 6 neighbours of the block it sets, so a redstone block set 2
  above a piston does not make it check. It stays retracted until some block next to it
  changes.
- `DispenserBlock.neighborChanged` (the dropper inherits it): powered is
  `hasNeighborSignal(pos) || hasNeighborSignal(pos.above())`. Powered and not triggered, it
  schedules its tick 4 later and sets `triggered=true` (flags 2) at once; not powered and
  triggered, it sets `triggered=false`.
- `DispenserBlock.dispenseFrom` and `DropperBlock.dispenseFrom`: an empty one plays world event
  1001 (the click) and dispenses nothing.
