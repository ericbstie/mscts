# Control: what differs in every join — 2026-10-01

Evidence behind #17: what two vanilla servers send differently in every
join, so that every Group compares the join without Masks of its own.

All facts are **verified** in this container, against vanilla 26.3 (the
Reference). Bytecode was read with `scripts/research/javap.py` from the
Reference jar. Live runs used a research probe (not committed) that
joined one Bot, an operator, to five fresh vanilla Instances with the
default ServerSpec, and recorded every packet it received.

## The login's session id

- `login_finished` carries a `session_id` (a UUID) after the profile.
- The server takes it from `ServerConnectionListener.getSessionId()`,
  which draws `UUID.randomUUID()` the first time it is asked and sets it
  back to null in `tick()` once no connection is left. Players who are
  connected at the same time share one id; a new one is drawn after the
  last leaves.
- The client hands it to `ClientTelemetryManager.createWorldSessionManager`
  (`ClientHandshakePacketListenerImpl.handleLoginFinished`) and to nothing
  else, so a player cannot see it.
- Live: it differed in every one of the five boots.

So `login_finished.session_id` is the first of `compare.RANDOM_FIELDS`,
which every Comparison masks (ADR-0011).

## The order of the tag lists

- `TagNetworkSerialization.serializeTagsToNetwork` collects the
  registries with `Collectors.toMap`, a `HashMap` keyed by each
  registry's `ResourceKey`. `serializeToNetwork(registry)` fills a
  `HashMap<Identifier, IntList>` from the `registry.getTags()` stream. The
  packet lists both in the order of those maps, and the live runs below
  show both orders change from one boot to the next.
- Each tag's entries come from `TagLoader.tryBuildTag`, which adds them to
  a `LinkedHashSet` in the order of the tag files and then copies it with
  `List.copyOf`. That order is the same every boot.
- The client decodes the registries into an `IdentityHashMap` and each
  registry's tags into a `HashMap` (`ClientboundUpdateTagsPacket.
  STREAM_CODEC`, `TagNetworkSerialization$NetworkPayload.STREAM_CODEC`),
  so neither order changes what it holds. The entries decode into an
  `IntArrayList`, whose order counts. The full chain is in
  `docs/PLAN.md`, Comparison semantics, step 1.
- Live, `update_tags` in configuration (58,754 bytes, 15 registries):
  - the registry order of boots 3 and 5 differs from that of boots 1, 2
    and 4;
  - between boots 1 and 2, the tag order differs in 9 of the 15
    registries;
  - every boot sends the same tags with the same entries in the same
    order, and no name twice.
- Pumpkin (one join to the nightly in the shared cache) sends the
  registries sorted by name.

So `compare.UNORDERED` sorts the registries and their tags by name before
anything else, keeping each tag's entries in order. The recorded
`update_tags` and `login_finished` of boots 1 and 3 are in
`tests/compare/data/`.
