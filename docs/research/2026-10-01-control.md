# Control: commands, their answers and a barrier — 2026-10-01

Evidence behind #17: the packets a command travels in, who hears what a
command says, the command tree each server sends, how Control knows a
command has run, and what two vanilla servers send differently in every
join.

All facts are **verified** in this container, against vanilla 26.3 (the
Reference) and Pumpkin nightly sha256 `b8382a8a…` (the binary says
commit `4426d11`). Bytecode was read with `scripts/research/javap.py`
from the Reference jar, and Pumpkin's source at `4426d11` on GitHub. The
wiki pages are `Java_Edition_protocol/Packets` revision 3790659 (26.3,
protocol 777) and `Java_Edition_protocol/Command_data` revision 3445801
(2026-02-20), read as raw wikitext. Live runs used research probes (not
committed) with the default ServerSpec and one operator Bot, and a
second Bot where a section says so.

## The packets

| Packet | javap | wiki |
|---|---|---|
| serverbound play `chat_command` | `readUtf()` / `writeUtf(String)`, whose default maximum is 32767: one String(32767), `command` | Command, String (32767), "excluding the `/`" |
| clientbound play `system_chat` | `StreamCodec.composite(ComponentSerialization.TRUSTED_STREAM_CODEC content, ByteBufCodecs.BOOL overlay)` | Content, Text Component; Overlay, Boolean |
| clientbound play `commands` | `composite(ENTRY list, VAR_INT root_index)`; the list is `ByteBufCodecs.list` (a VarInt count) | Nodes, Prefixed Array of Node; Root index, VarInt |

The wiki agrees with the bytecode on all three. The content of
`system_chat` is a text component in network NBT; mscts keeps it as NBT
bytes until text components have a codec.

### A node of the command tree

`ClientboundCommandsPacket$Entry.write` and `readNode`:

- Byte flags. The low two bits are the node type (`MASK_TYPE` 3): 0 root,
  1 literal, 2 argument; 3 is never written. Then `EXECUTABLE` 4,
  `REDIRECT` 8, `CUSTOM_SUGGESTIONS` 16, `RESTRICTED` 32.
- VarInt array of child indices.
- VarInt redirect index, only if flags & 8.
- A literal: its name, `readUtf()`.
- An argument: its name, `readUtf()`; a VarInt parser id
  (`BuiltInRegistries.COMMAND_ARGUMENT_TYPE.byId`); the parser's
  properties; then an Identifier naming its suggestions, only if
  flags & 16.
- A root has no more data.

The wiki (Command data) gives the same layout and flags. When the client
does not know a parser id, `byId` returns null and the node has no data
after it: the rest of the packet cannot be read.

### Parser ids and properties

The ids are the protocol order of the `minecraft:command_argument_type`
registry: 62 parsers in 26.3, 0 `brigadier:bool` to 61 `minecraft:uuid`
(`registries.json` from the data generator; mscts reads them with
`codec.registry_names`). The wiki lists 57 (0 to 56), from an older
version:

- it calls 16 `minecraft:color`; 26.3 calls it `minecraft:team_color`;
- it lacks `context_float_provider` (55), `context_int_provider` (56),
  `slot_source` (57), `feature` (59) and `swing_animation` (60);
- so `dialog` is 58 and `uuid` 61 in 26.3, not 55 and 56.

Properties, from `ArgumentTypeInfos.bootstrap` and each info's
`serializeToNetwork` / `deserializeFromNetwork` (the wiki agrees):

| Parser | Properties |
|---|---|
| `brigadier:float`, `brigadier:double`, `brigadier:integer`, `brigadier:long` | Byte flags (1 has a minimum, 2 has a maximum), then the minimum if flags & 1 and the maximum if flags & 2, each a Float, Double, Int or Long |
| `brigadier:string` | VarInt enum: 0 `SINGLE_WORD`, 1 `QUOTABLE_PHRASE`, 2 `GREEDY_PHRASE` (brigadier 1.3.11, `StringArgumentType$StringType`) |
| `minecraft:entity` | Byte flags: 1 a single entity, 2 players only |
| `minecraft:score_holder` | Byte flags: 1 allows several |
| `minecraft:time` | Int, the minimum in ticks |
| `minecraft:resource_or_tag`, `minecraft:resource_or_tag_key`, `minecraft:resource`, `minecraft:resource_key`, `minecraft:resource_selector` | Identifier, the registry (`readRegistryKey`) |
| every other parser | nothing |

### The trees each server sends

A scratch decoder with this table read both recorded operator trees to
the last byte:

| | Vanilla | Pumpkin |
|---|---|---|
| bytes | 35,095 | 19,735 |
| nodes | 2,399 | 1,402 |
| root index | 0 | 0 |
| root literals | 92 | 100 |
| `RESTRICTED` (32) | set on some nodes | never |
| non-operator tree | 265 bytes | 19,578 bytes |

- Pumpkin's root literals that vanilla lacks: `?`, `banip`, `h`,
  `pardonip`, `plugin`, `plugins`, `pumpkin`, `tps`, `ver`. Vanilla's that
  Pumpkin lacks: `jfr`, `perf`.
- Both have `setblock`, `tick` and `tellraw`.
- Pumpkin uses `team_color`, `context_float_provider` and
  `context_int_provider`, and the suggestions `ask_server` and
  `summonable_entities`.

So Control decides whether a Candidate has a command from the root
literals of the tree its own Bot received.

## Who hears what a command says

- `CommandSourceStack.sendSuccess(message, allowLogging)` sends the
  message to the source if `source.acceptsSuccess()` and the stack is not
  silent. A player's source (`ServerPlayer$3`) accepts success only if
  the game rule `send_command_feedback` is on (default true); it always
  accepts failure.
- If `allowLogging`, the source `shouldInformAdmins()` (a player's always
  does) and the stack is not silent, it calls `broadcastToAdmins`: the
  message wrapped in `chat.type.admin`, gray and italic, sent to every
  **other** player who is an operator, if `send_command_feedback` is on.
  It also goes to the server log if `log_admin_commands` is on.
- So a Group's own Bots stay non-operators: an operator Bot would receive
  every Control command's feedback.
- `tellraw` (`TellRawCommand`) only calls `ServerPlayer.sendSystemMessage`
  for each target: no feedback, no admin broadcast.
- Vanilla kicks a player who sends commands too fast
  (`detectCommandRateSpam`, `disconnect.spam`), but never an operator
  (`PlayerList.isOp`). Pumpkin's `check_chat_spam` skips operators too
  when its `ops_bypass` setting is on.

## The Control barrier

A Group's window ends with `Bot.sync()`: two `client_command`
(`REQUEST_STATS`) round trips, each handled at the start of a tick
(`docs/research/2026-09-30-observation-window.md`). That is not enough
after a command.

### Why `Bot.sync()` alone misses a command's effects — vanilla

- `handleChatCommand` → `tryHandleChat` → `server.execute`: the command
  is a `TickTask` in the server's task queue, which runs between ticks
  (`waitUntilNextTick` → `runAllTasks`, `managedBlock`).
- That queue is first in, first out, and stops at its head: a task runs
  only if `shouldRun(task)`, which is `task.tick + 3 < tickCount ||
  haveTime()`.
- When the server is behind schedule, `runServer` runs the next tick at
  once, with no time left, so a queued command can wait up to three
  ticks. `REQUEST_STATS` is still answered at the start of each of those
  ticks.
- Live, the probe Group (`setblock` inside a window, vanilla on both
  sides, 4 rounds of 20): 8 of 80 plays lost the `block_update` from one
  side's window, for both Bots. In each, the two `award_stats` answers
  came 0.5–2 ms apart (ticks back to back), and once the command's own
  `system_chat` came after both.

### The marker

After the command, Control sends a second command, `tellraw @s
"<token>"`, waits for the `system_chat` whose bytes hold the token, then
calls `Bot.sync()`.

- Vanilla: the marker is a `TickTask` in the same queue, behind the
  command, so its answer means the command has run. `Bot.sync()` then
  waits for a whole tick to broadcast what the command changed. `tellraw`
  changes nothing and says nothing else.
- Live, vanilla, the same probe Group with the marker, 4 rounds of 20:
  0 of 80 plays odd.
- The token is a fixed prefix and a counter, so no other message can
  hold it. Control never waits for "the next `system_chat`": on Pumpkin
  the operator's own join message arrived inside the first command's
  wait.

### Pumpkin runs commands at the same time

- `handle_play_packet` (`net/java/mod.rs`) runs every `chat_command` in
  its own task (`server.spawn_task(async { handle_chat_command(…) })`).
  `handle_chat_command` then runs the command at once
  (`dispatcher.handle_command`). Nothing orders two commands from one
  player.
- `client_command` is handled in `Player::tick`
  (`process_inbound_packets`, at most 64 packets each tick).
- Live, one operator Bot, 20 plays of 6:
  - `setblock`, then the marker, then `Bot.sync()`: the `block_update`
    came before the barrier's end every time (0 of 120 late).
  - `fill` over 28,830 blocks, then the marker at once: on Pumpkin the
    marker answered before the fill's feedback in 18 of 18 (the marker
    about 49 ms after the fill was sent, the feedback about 60 ms). On
    vanilla, 0 of 18.

### What follows

- On vanilla the marker is exact: one queue, in order.
- On Pumpkin a command that takes more than about a tick longer than the
  marker can land after the barrier. That is a real difference from
  vanilla (a player's commands answer out of order), and it shows where
  it lands. The order of a player's commands is a test case for #66.
- A Group keeps its setup commands before its window, and small. One
  that needs a large setup (a big `fill`) checks it has finished with a
  command that answers, such as `execute if block …`, before it opens its
  window.

## The login's session id

- `login_finished` carries a `session_id` (a UUID) after the profile.
- The server takes it from `ServerConnectionListener.getSessionId()`,
  which draws `UUID.randomUUID()` the first time it is asked and sets it
  back to null in `tick()` once no connection is left. Players who are
  connected at the same time share one id; a new one is drawn after the
  last leaves.
- The client hands it to `ClientTelemetryManager.createWorldSessionManager`
  (`ClientHandshakePacketListenerImpl.handleLoginFinished`) and to nothing
  else, so a player cannot see it.
- Live: it differed in every one of five vanilla boots.

So `login_finished.session_id` is the first of `compare.RANDOM_FIELDS`,
which every Comparison masks (ADR-0011).

## The order of the tag lists

- `TagNetworkSerialization.serializeTagsToNetwork` collects the
  registries with `Collectors.toMap`, a `HashMap` keyed by each
  registry's `ResourceKey`. `serializeToNetwork(registry)` fills a
  `HashMap<Identifier, IntList>` from the `registry.getTags()` stream. The
  packet lists both in the order of those maps, and the live runs below
  show both orders change from one boot to the next.
- Each tag's entries come from `TagLoader.tryBuildTag`, which adds them to
  a `LinkedHashSet` in the order of the tag files and then copies it with
  `List.copyOf`. That order is the same every boot.
- The client decodes the registries into an `IdentityHashMap` and each
  registry's tags into a `HashMap` (`ClientboundUpdateTagsPacket.
  STREAM_CODEC`, `TagNetworkSerialization$NetworkPayload.STREAM_CODEC`),
  so neither order changes what it holds. The entries decode into an
  `IntArrayList`, whose order counts. The full chain is in
  `docs/PLAN.md`, Comparison semantics, step 1.
- Live, `update_tags` in configuration (58,754 bytes, 15 registries), one
  operator Bot joined to five fresh vanilla Instances:
  - the registry order of boots 3 and 5 differs from that of boots 1, 2
    and 4;
  - between boots 1 and 2, the tag order differs in 9 of the 15
    registries;
  - every boot sends the same tags with the same entries in the same
    order, and no name twice.
- Pumpkin (one join to the nightly in the shared cache) sends the
  registries sorted by name.

So `compare.UNORDERED` sorts the registries and their tags by name before
anything else, keeping each tag's entries in order. The recorded
`update_tags` and `login_finished` of boots 1 and 3 are in
`tests/compare/data/`.
