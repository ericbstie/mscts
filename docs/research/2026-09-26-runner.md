# Runner research — 2026-09-26

Facts about starting and stopping servers, found while building
`mscts.runner`. Everything marked **verified** was observed first-hand in
this container against vanilla 26.3 (jar sha1 `33680f5f…`, Temurin 25) via
`running()` with the `VanillaAdapter` LaunchPlan.

## Vanilla readiness and stop — verified

- **TCP accepts before vanilla is ready.** Vanilla binds its port at
  `Starting Minecraft server on 127.0.0.1:<port>`, before
  `Preparing level "world"` and `Done`. It answers a status ping only
  later: with 20 ms polling, the first status answer came 0.75 s (cold)
  and 0.26 s (warm) after the first accepted TCP connection. So a TCP
  connect is not a readiness probe (ADR-0004). Readiness is the status
  ping.
- **A console line vanilla reads before its world exists is lost.** A
  `stop` written as soon as TCP accepted, which was before the overworld
  existed, failed when it ran just after `Done`:

  ```
  [Server thread/ERROR] [net.minecraft.commands.Commands]: Command exception: /stop
  java.lang.NullPointerException: Cannot invoke "net.minecraft.server.level.ServerLevel.getGameRules()"
    because the return value of "net.minecraft.commands.CommandSourceStack.getLevel()" is null
      at net.minecraft.commands.Commands.executeCommandInContext(Commands.java:432)
      ...
      at net.minecraft.server.dedicated.DedicatedServer.handleConsoleInputs(DedicatedServer.java:412)
  ```

  The console's command source is built when the line is read. At that
  point it has no level, and the command throws when it runs. At the
  default log level vanilla only logs
  `System chat: An unexpected error occurred while trying to execute that command`
  and then keeps running. It reproduced 4 of 4 times, on cold and warm
  boots. To see the stack trace, pass a log4j2 config that sets
  `net.minecraft.commands.Commands` to `debug`, with
  `-Dlog4j2.configurationFile=<file>`. Consequence: send console commands,
  including `stop`, only after the status ping answers.
- **`stop` after the status ping answers** is graceful: exit code 0, in
  1.37 s on the first boot and 0.42 s on the second. Both include the
  world save.
- **SIGTERM** runs vanilla's shutdown hook: `world/level.dat` was
  rewritten at the moment of the signal, and the exit code was 143. After
  the signal nothing more was logged to the console or to
  `logs/latest.log`.
- **Startup time**, from launch to the first status answer: 10.6 s for a
  fresh workdir and 10.1 s for the same workdir again. About 7 s of that
  passes before vanilla's first log line (JVM start, the bundler, and
  bootstrap). `Done (0.7s)` covers only the level preparation. Other
  workers may have been using the machine at the same time.

## Container — verified

- PID 1 (`process_api`) reaps orphans lazily. An orphaned grandchild
  stays a zombie for 1–3 s. So a test that checks a process that is not
  its own child must count a zombie as dead.
- `pid_max` is 32768, so PIDs are reused sooner than on a default host.
