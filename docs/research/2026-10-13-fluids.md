# How water and lava spread, make sources and turn to stone, tick by tick — 2026-10-13

Evidence for #38, the `fluids` Groups. Facts are **verified** with `scripts/research/javap.py`
on the 26.3 server jar unless a line says *live* (two vanilla 26.3 Instances, 2026-10-13).

## Delays and distances

- Water: `WaterFluid.getTickDelay` 5, `getDropOff` 1, `getSlopeFindDistance` 4. A source has
  amount 8, so water reaches 7 blocks out, one block every 5 ticks.
- Lava: `LavaFluid.getTickDelay` 30 (10 where `isFastLava`, the Nether), `getDropOff` 2 (1),
  `getSlopeFindDistance` 2 (4). In the Overworld lava reaches 3 blocks out, one block every 30
  ticks.
- `LiquidBlock.onPlace` and `neighborChanged` schedule the fluid's tick `getTickDelay` later.
  So does `LiquidBlock.updateShape` when the block or its neighbour is a source.
- `FlowingFluid.tick`: a block that is not a source takes `getNewLiquid`; if that is empty it
  becomes air, if it differs it is set and its next tick scheduled `getSpreadDelay` later. Then
  `spread`.
- `FlowingFluid.spread` tries down first; it spreads to the sides only if it could not go down,
  or if it went down with 3 or more sources beside it. A block that is not a source and has a
  hole under it (`isWaterHole`) does not spread to the sides.
- `spreadToSides` gives the sides the amount less the drop-off (7 for a falling fluid) and
  `getSpread` picks the sides: only those with the shortest way down within the slope distance,
  or all four if there is none. `getSpread` returns an `EnumMap`, so the sides go in `Direction`
  order on every server.
- `FlowingFluid.getSpreadDelay` is the tick delay. `LavaFluid.getSpreadDelay` multiplies it by 4
  when the old and new fluid are both there and neither is falling, the new one is higher, and
  `level.getRandom().nextInt(4) != 0`. That is random, and happens only when a flowing lava's own
  tick raises its level. A lava that only spreads out from one source never does: each block is
  first set by its shortest way from the source, which is its highest level.
- `LavaFluid.randomTick` lights fires, on random ticks only.

## New sources

- `FlowingFluid.getNewLiquid` counts the sources of the same fluid beside a block. With 2 or
  more, `canConvertToSource`, and a solid block or a source of the same fluid under it, the block
  becomes a source. `getSpread` computes the side's fluid with `getNewLiquid`, so the block
  between two sources becomes a source on the first tick a source spreads into it.
- `WaterFluid.canConvertToSource` reads the game rule `water_source_conversion` (default true),
  `LavaFluid.canConvertToSource` reads `lava_source_conversion` (default false). The rule is read
  when the tick runs.

## Lava meets water

- `LiquidBlock.shouldSpreadLiquid`, from `onPlace` and `neighborChanged`, for lava only: for each
  of the blocks above and beside it, water there turns the lava to obsidian if the lava is a
  source, else to cobblestone; with soul soil under the lava, blue ice there turns it to basalt.
  Each calls `fizz`. It happens in the tick of the change that placed or neighboured the lava,
  with no delay.
- `LavaFluid.spreadTo` going down into water sets the water to stone (if it is a
  `LiquidBlock`) and calls `fizz`.
- `fizz` is `levelEvent(1501, pos, 0)`: the client plays the fizz sound and the smoke. The server
  sends no `sound` for it.

## A frozen world

- The fluid ticks run only on the ticks the world steps, and a frozen world's game time stands
  still (docs/research/2026-10-03-tick-step.md). A placement made between steps is due on the
  step its delay says, wherever it ran in the real time between them.
- *Live*: `Control.run` passes the barrier after each command, so a placement's
  `block_update` arrives on its own, before the next step, and never together with what that
  step changes.
- A scheduled tick is kept per block and fluid, with its due time: `LevelChunkTicks.schedule`
  adds a tick only if its set (`ScheduledTick.UNIQUE_TICK_HASH`, by type and position, as
  `ScheduledTick.probe` builds) has none for that block and fluid yet, and `poll` takes it out
  of the set when it runs. A second tick for the same block and fluid is dropped. Ticks run in
  `DRAIN_ORDER`: due time, priority, then the order they were scheduled in. A source and a
  flowing fluid are different types (`LAVA`, `FLOWING_LAVA`), and `ServerLevel.tickFluid` runs a
  tick only on the fluid of its type. A tick still due when a Group ends runs later, on whatever is at the block
  then. A source scheduled tick left due would run on a source placed at the same block by the
  next play, before its own, and spread early. So each Group steps until every source has had
  its last scheduled tick. A flowing fluid's tick left due is harmless: it is due within one
  delay of the window's end, and no flowing fluid of the next play exists that early.
- Time between plays does not run such a tick out. `LevelChunkTicks.pack` saves a tick as its
  due time less the game time, and `unpack` schedules it that far after the chunk loads again.
  So a tick due when the players left chunk (0, 0) comes back as due when the next play joins.
- Clearing a Group's blocks schedules ticks too. `FillCommand.fillBlocks` places each block with
  flags 2 | 256, which update the shape of the blocks beside it (no `UPDATE_KNOWN_SHAPE`), and
  then calls `updateNeighboursOnBlockSet` for each. A lava or water source next to a block the
  fill has cleared, and not yet cleared itself, gets its tick scheduled by `updateShape`. With
  `strict` the flags are 2 | 816, which skip the shape updates, and there is no neighbour pass.
  *Live*: with a plain fill, 1 of the first 2 plays of `fluids/lava-spread` did not match: on one
  Instance its middle source spread on tick 16, on the other on tick 12, instead of 30. The
  Groups clear with a strict fill.

## Live

- `fluids/water-spread` (a draft, one play on each of two Instances): a source at the floor's
  middle sends one `section_blocks_update` every 5 ticks, from tick 5 to 35, a level less each
  ring, with the same blocks in the same order on both sides. A source 3 blocks from a hole
  flows only toward it, a block on ticks 6, 11 and 16, and falls in on tick 21. The
  placements arrive on ticks 1 and 2. With the strict clear, 20 more plays
  (`scripts/research/probe_loop.py`) all matched.
- `fluids/lava-spread` (a draft): rings on ticks 30, 60 and 90; the source 2 blocks from the
  hole reaches it on 31 and 61 and falls in on 91.
- `fluids/sources` (a draft): water becomes a source on tick 9 with the rule on, and stays
  flowing (level 1) from tick 15 with it off. Lava becomes a source on tick 30, and stays
  flowing (level 2) from 32.
- `fluids/interactions` (a draft): obsidian on tick 10, stone on 31, cobblestone on 32, basalt
  on 33, each with a `level_event` 1501 just before its block change. Nothing changes after.
