# Join research — 2026-09-26

Facts behind the join brief: the protocol layer's edge cases, the connection
State machine, and what the vanilla client does on the way to play. Every
fact marked **verified (javap)** was read with `javap -c -p -constants` from
the 26.3 jars (protocol-research skill):

- the server: `META-INF/versions/26.3/server-26.3.jar` inside the bundler
  `server.jar` (sha1 `33680f5f…`);
- the client: `client.jar` (sha1 `e877b6a0…`, from the 26.3 version JSON,
  cached at `<cache_dir>/research/vanilla-client/26.3/client.jar`). Like the
  server, the 26.x client ships unobfuscated, so client-side questions (which
  the server jar cannot answer) are settled the same way.

Classes shared by both sides (`net.minecraft.network.*`) are identical.

## Wire types

- **VarInt / VarLong truncate** (verified (javap), `VarInt.read`,
  `VarLong.read`): `out |= (b & 127) << (n++ * 7)` with a 32-bit `ishl`
  (64-bit `lshl`), then "VarInt too big" once a 6th (11th) byte has been
  read. So the unused high bits of a 5th (10th) byte fall off:
  `ff ff ff ff 7f` reads as −1, `80 80 80 80 10` as 0. The Codec reads them
  the same way. This is the protocol's definition, not a client leniency:
  minecraft.wiki *VarInt and VarLong* (raw wikitext, oldid 3772026) says
  "unnecessarily long encodings (e.g. `81 00` to encode 1) are allowed", and
  its sample decoder does the same arithmetic in Java `int`/`long`.

- **NBT on the network** (verified (javap), `NbtIo`, `ListTag`, `NbtAccounter`):
  an unnamed root (a type byte, then its payload; TAG_End alone means no
  tag). Lists and compounds may nest at most 512 deep (`MAX_STACK_DEPTH`,
  `pushDepth` throws once depth reaches it), a list with element type End
  and a positive length is "Missing type on ListTag", an unknown type id
  fails. Registry data reads it under a 2 MiB accounting quota
  (`DEFAULT_NBT_QUOTA`), which the Codec does not model.

## The State machine, as the vanilla client runs it

- **Terminal packets** (verified (javap), every `Packet.isTerminal()` in the
  client jar): clientbound `login_finished`, configuration
  `finish_configuration`, play `start_configuration`; serverbound
  `intention`, `login_acknowledged`, configuration `finish_configuration`,
  play `configuration_acknowledged`.
- **Inbound switches on receipt** (verified (javap), `PacketDecoder.decode`
  → `ProtocolSwapHandler.handleInboundTerminalPacket`): after decoding a
  terminal packet the decoder turns auto-read off and removes itself, and
  the listener installs the next State's decoder
  (`setupInboundProtocol`) before anything else is decoded. So every frame
  after `login_finished` is configuration, even before the client acks.
- **Outbound switches after the ack** (verified (javap),
  `ClientHandshakePacketListenerImpl.handleLoginFinished`,
  `ClientConfigurationPacketListenerImpl.handleConfigurationFinished`):
  `setupInboundProtocol(next)`, then `send(ack)`, then
  `setupOutboundProtocol(next)`. `handleLoginFinished` then sends a brand
  `custom_payload` and `client_information`, and so does the Bot (`Replies`).
- **Compression** (verified (javap), `handleCompression`): handled on the
  network thread as it is decoded, `setupCompression(threshold, false)`,
  both directions at once, so it applies from the next frame.

## Framing and compression

- **A negative threshold means no compression** (verified (javap),
  `Connection.setupCompression(int, boolean)` starts `iload_1; iflt`, and
  that branch removes the `decompress` and `compress` handlers). A
  threshold of 0 or more installs (or updates) both. The wiki's *Set
  Compression* agrees: "Negative values will disable compression".
- **Frame length** (verified (javap), `Varint21FrameDecoder.decode`): at most
  3 VarInt bytes ("length wider than 21-bit", so at most 2 097 151), and
  never 0 ("Frame length cannot be zero"). Both are `CorruptedFrameException`,
  which ends the connection. The encoder side (`Varint21LengthFieldPrepender`)
  throws when the length needs more than 3 bytes, and `CompressionEncoder`
  throws for more than 8 388 608 bytes of data ("Packet too large"), before
  deciding whether to compress.
- **Decompression** (verified (javap), `CompressionDecoder`): data-length 0
  passes the rest through. Otherwise, only with `validateDecompressed`, a
  data-length below the threshold or above `MAXIMUM_UNCOMPRESSED_LENGTH`
  (8 388 608) is a `DecoderException`. The **server** passes `true`; the
  **client** passes `false`
  (`ClientHandshakePacketListenerImpl.handleCompression` calls
  `setupCompression(threshold, false)`). Then `inflate` allocates a direct
  buffer of exactly data-length bytes (a negative one throws), inflates once
  into it, and throws unless it got exactly that many bytes. So a longer
  stream is truncated, not rejected, and nothing after the declared length
  (the rest of the stream, its Adler-32 trailer, trailing bytes) is read.
- **Bool** (the audit, `AbstractByteBuf.readBoolean`): `readByte() != 0`.
- **String** (verified (javap), `Utf8String.read`): a byte length above
  `utf8MaxBytes(n)` = 3n, or negative ("Weird string!"), throws; so does a
  decoded length above n UTF-16 units. The bytes are decoded with
  `ByteBuf.toString(UTF_8)`, which replaces malformed UTF-8.

## The join, as the vanilla client and server run it

- **Offline login** (verified (javap), server
  `ServerLoginPacketListenerImpl.handleHello`): the name must pass
  `StringUtil.isValidPlayerName` (at most 16 chars, each in 33‥126, else
  "Invalid characters in username"). Without authentication the server
  ignores the hello's UUID and uses `UUIDUtil.createOfflineProfile(name)`:
  `createOfflinePlayerUUID` is `UUID.nameUUIDFromBytes` (MD5, version 3)
  of `"OfflinePlayer:" + name` in UTF-8 (the concat recipe
  `OfflinePlayer:\u0001`, `javap -v`). Java 25 computes
  `b50ad385-829d-3141-a216-7e7d7539ba7f` for Notch and
  `40f5db53-a47a-33ee-b1f6-db0e20deded4` for alice. With authentication it
  sends the encryption request (login `hello`) instead.
- **login_disconnect** (verified (javap), `ClientboundLoginDisconnectPacket`):
  the reason is `ByteBufCodecs.lenientJson(262144)`, a JSON text component
  as a String of up to 262 144 chars, more than `String (n)` allows, so the
  Codec leaves it raw.
- **Known packs** (verified (javap), client `KnownPacksManager`): the client
  answers `select_known_packs` with the offered packs it has, in the
  server's order. Vanilla offers only `minecraft:core` at the Target's
  version, which the vanilla client has, so it echoes the offer.
- **Teleport** (verified (javap), client `ClientPacketListener.handleMovePlayer`,
  `PositionMoveRotation.calculateAbsolute`, `Entity.setYRot` / `setXRot`):
  the client applies the pose (each part flagged relative adds to the current
  value, rotation summed as floats, pitch clamped to ±90, a non-finite
  rotation keeps the old one) and sends `accept_teleportation` with the id
  and the resulting x, y, z, yaw and pitch. In 26.3 it sends no movement
  packet there.
- **Chunk batches** (verified (javap), server `PlayerChunkSender`): the
  server starts at 9 chunks per tick (`START_CHUNKS_PER_TICK`), clamps the
  rate a `chunk_batch_received` asks for to 0.01‥64 (NaN → 0.01), and
  allows one unacknowledged batch until the first acknowledgement, 10 after.
- **Keep-alive** (verified (javap), server
  `ServerCommonPacketListenerImpl.keepConnectionAlive`, `handleKeepAlive`):
  each listener (configuration, then play) starts its clock when it is
  created. Once 15 000 ms have passed since the last keep-alive it either
  disconnects the client ("Timed out") if that keep-alive is still pending,
  or sends a new one whose id is the server's millisecond clock. A
  keep-alive that is not the pending one's id disconnects at once. So in
  play the first keep-alive comes ~15 s after the play listener starts, and
  a client that answered it gets the next one ~15 s later.

## What the client sends by itself (issue #16, 2026-09-30)

Every fact here is **verified (javap)** on the same 26.3 jars, unless it
says otherwise. Field layouts: minecraft.wiki `Java_Edition_protocol/Packets`,
revision 3790659 ("26.3, protocol 777"), raw wikitext.

### After `login_finished`

- **Order** (client `ClientHandshakePacketListenerImpl.handleLoginFinished`,
  offsets 106–174): `setupInboundProtocol(configuration)`, send
  `login_acknowledged`, `setupOutboundProtocol(configuration)`, then send
  configuration `custom_payload(BrandPayload(ClientBrandRetriever.getClientModName()))`,
  then configuration `client_information(minecraft.options.buildPlayerInformation())`.
  All three go out before the client handles the next frame.
- **Brand**: `ClientBrandRetriever.getClientModName()` returns the constant
  `VANILLA_NAME = "vanilla"`. `BrandPayload.TYPE` is
  `CustomPacketPayload.createType("brand")` (`minecraft:brand`), and its
  codec writes the brand with `FriendlyByteBuf.writeUtf` (a String, max
  32767). On the wire: channel Identifier `minecraft:brand`, then the
  String `vanilla` (`07 76 61 6e 69 6c 6c 61`). The serverbound
  `ServerboundCustomPayloadPacket` codec reads a known channel with its own
  codec and any other with `DiscardedPayload.codec(id, 32767)`; the wiki
  layout is "Channel Identifier, Data (rest of the packet)".
- **`client_information` layout** (`ClientInformation.write` and its
  `FriendlyByteBuf` constructor): language String (the server reads at most
  16), view distance Byte (`writeByte`), chat visibility, chat colors
  Boolean, model customisation Unsigned Byte (`readUnsignedByte`), main
  hand, text filtering Boolean, allows listing Boolean, particle status.
  The three enums use `ByteBufCodecs.idMapper`, whose codec
  (`ByteBufCodecs$31`) is a VarInt id. Ids: `ChatVisiblity` FULL 0,
  SYSTEM 1, HIDDEN 2; `HumanoidArm` LEFT 0, RIGHT 1; `ParticleStatus` ALL 0,
  DECREASED 1, MINIMAL 2. The wiki agrees field by field.
- **What a fresh client sends** is `Options.buildPlayerInformation()`, not
  `ClientInformation.createDefault()`. With a fresh `options.txt`, the
  `Options` constructor sets:

  | Field | Value | Source |
  | --- | --- | --- |
  | language | `en_us` | `Options.<init>`: `languageCode = "en_us"` |
  | view distance | 12 | `renderDistance`: `OptionInstance(…, IntRange(2, 16 or 32), 12)`: 32 is the maximum with at least 1 GB of heap |
  | chat visibility | FULL (0) | `chatVisibility`: `ChatVisiblity.FULL` |
  | chat colors | true | `chatColors`: `createBoolean("options.chat.color", true)` |
  | model customisation | 127 (0x7F) | `modelParts = EnumSet.allOf(PlayerModelPart)`; `buildPlayerInformation` ORs each `getMask()` = `1 << bit`, bits 0–6 (cape … hat) |
  | main hand | RIGHT (1) | `mainHand`: `HumanoidArm.RIGHT` |
  | text filtering | false | `Minecraft.isTextFilteringEnabled()` reads the account's `PROFANITY_FILTER_ENABLED` flag from Mojang's user API. A Bot has no account, so false (the wiki: "In offline mode, it is always false") |
  | allows listing | true | `allowServerListing`: `createBoolean(…, true, …)` |
  | particle status | ALL (0) | `particles`: `ParticleStatus.ALL` |

  `ClientInformation.createDefault()` (`en_us`, **2**, FULL, true, **0**,
  `Player.DEFAULT_MAIN_HAND`, false, false, ALL) is what the **server**
  assumes until the client's own arrives: the login listener builds the
  first `CommonListenerCookie` with `createInitial`, which uses
  `createDefault()`. The configuration listener replaces it on
  `handleClientInformation`, and `ServerPlayer.updateOptions` applies it.
  So a client that sends none plays with view distance 2, no skin parts
  and allows listing false.

### How the server combines view distances

- `ChunkMap.getPlayerViewDistance(player)` is
  `Mth.clamp(player.requestedViewDistance(), 2, serverViewDistance)`, and
  `setServerViewDistance` clamps the server's own to 2‥32. So a player's
  view distance is the smaller of the two, at least 2.
- A Bot sends 12, like a fresh client, so it never limits a server whose
  view distance is at most 12 (the ServerSpec default is 2). Above 12, the
  Bot sees 12, as a player with default settings would.
- The chunks a player tracks (`ChunkTrackingView.of(center, v)`, the
  `Positioned` record) are those in `[c − v − 1, c + v + 1]²` for which
  `isWithinDistance(…, includeOuter = true)` holds:
  `max(0, |dx| − 2)² + max(0, |dz| − 2)² < v²`. That is 49 chunks at
  view distance 2 and 117 at 4 (the 11 × 11 square without its 4 corners).

### `player_loaded`

- **Where the client sends it** (client `ClientPacketListener.tick`, offsets
  119–149, and `notifyPlayerLoaded`): on each client tick it calls
  `levelLoadTracker.tickClientLoad()`, and once `isLevelReady()` holds it
  sends `ServerboundPlayerLoadedPacket` (no fields; `StreamCodec.unit`) if
  it has not already (`clientLoaded`), then drops the tracker.
  `clientLoaded` is reset by `handleLogin` and `handleRespawn`.
- **When `isLevelReady()` holds** (`LevelLoadTracker` and its states):
  `startClientLoad` (at login) starts in `WaitingForServer`; the game event
  `LEVEL_CHUNKS_LOAD_START` (the server sends it in
  `PlayerList.sendLevelInfo`, before any chunk) moves it to
  `WaitingForPlayerChunk`. That state's `tick` becomes `ClientLevelReady`
  once the renderer has compiled the section at the camera
  (`playerSectionReady`), or at once if the camera is outside the build
  height or the player is a spectator or dead, or after
  `CLIENT_WAIT_TIMEOUT_MS` (30 s: "Timed out while waiting for the client to
  load chunks, letting the player into the world anyway"). `isLevelReady`
  then waits `closeDelayMs` more.
- So the moment depends on the client's renderer and tick timing, which a
  Bot does not have. A Bot sends `player_loaded` once, right after its
  first chunk batch has finished (after `chunk_batch_received`). The server
  sends the pending chunks nearest the player first
  (`PlayerChunkSender.collectChunksToSend` sorts them by
  `ChunkPos.distanceSquared` to the player's chunk), so the first batch
  starts with the player's own chunk once it is ready. This is the
  earliest a real client could be ready, and it does not depend on timing.
  Only `join()` sends it: after a respawn, or a new `login` after
  reconfiguration, the vanilla client sends it again, and a Bot does not
  yet.
- **The wiki differs here**: its *Player Loaded* section says the client
  starts ticking the player after 60 ticks and then skips the packet
  completely. In 26.3 the client has no such timer: `clientLoaded` is set
  only by `notifyPlayerLoaded`, and after the 30 s timeout it still sends
  the packet. The 60 ticks are the server's (below). Until it has sent the
  packet, the client does not tick its player or send movement
  (`LocalPlayer.tick` and `sendChanges` return early while
  `hasClientLoaded()` is false).

### What the server does for a player not yet loaded

- `ServerGamePacketListenerImpl.hasClientLoaded()` is
  `!waitingForRespawn && clientLoadedTimeoutTimer <= 0`. The timer starts
  at `CLIENT_LOADED_TIMEOUT_TIME` = 60 ticks
  (`restartClientLoadTimerAfterRespawn`, called by the constructor and on
  respawn), drops by one each `ServerPlayer.tick`
  (`tickClientLoadTimeout`), and `handleAcceptPlayerLoad` sets it to 0. So
  without the packet the server treats the player as loaded 60 ticks
  (3 s) after joining.
- Until then:
  - **No damage.** `ServerPlayer.isInvulnerableTo` returns true for every
    damage source while `!hasClientLoaded()`.
  - **No movement.** `handleMovePlayer` and `handleMoveVehicle` return
    before applying the move, and `handlePlayerInput` records the input
    but skips the rest.
  - **No actions.** `handlePlayerAction` (digging, dropping, swapping),
    `handleUseItemOn`, `handleUseItem`, `handlePlayerCommand`,
    `handleAttack`, `handleInteract` and `handleSpectatorAction` return
    at once.
