# Join research — 2026-09-26

Facts behind the join brief: the protocol layer's edge cases, the connection
State machine, and what the vanilla client does on the way to play. Every
fact marked **verified (javap)** was read with `javap -c -p -constants` from
the 26.3 jars (protocol-research skill):

- the server: `META-INF/versions/26.3/server-26.3.jar` inside the bundler
  `server.jar` (sha1 `33680f5f…`);
- the client: `client.jar` (sha1 `e877b6a0…`, from the 26.3 version JSON,
  cached at `<cache_dir>/research/vanilla-client/26.3/client.jar`). Like the
  server, the 26.x client ships unobfuscated, so client-side questions (which
  the server jar cannot answer) are settled the same way.

Classes shared by both sides (`net.minecraft.network.*`) are identical.

## Wire types

- **VarInt / VarLong truncate** (verified (javap), `VarInt.read`,
  `VarLong.read`): `out |= (b & 127) << (n++ * 7)` with a 32-bit `ishl`
  (64-bit `lshl`), then "VarInt too big" once a 6th (11th) byte has been
  read. So the unused high bits of a 5th (10th) byte fall off:
  `ff ff ff ff 7f` reads as −1, `80 80 80 80 10` as 0. The Codec reads them
  the same way. This is the protocol's definition, not a client leniency:
  minecraft.wiki *VarInt and VarLong* (raw wikitext, oldid 3772026) says
  "unnecessarily long encodings (e.g. `81 00` to encode 1) are allowed", and
  its sample decoder does the same arithmetic in Java `int`/`long`.

- **NBT on the network** (verified (javap), `NbtIo`, `ListTag`, `NbtAccounter`):
  an unnamed root (a type byte, then its payload; TAG_End alone means no
  tag). Lists and compounds may nest at most 512 deep (`MAX_STACK_DEPTH`,
  `pushDepth` throws once depth reaches it), a list with element type End
  and a positive length is "Missing type on ListTag", an unknown type id
  fails. Registry data reads it under a 2 MiB accounting quota
  (`DEFAULT_NBT_QUOTA`), which the Codec does not model.

## The State machine, as the vanilla client runs it

- **Terminal packets** (verified (javap), every `Packet.isTerminal()` in the
  client jar): clientbound `login_finished`, configuration
  `finish_configuration`, play `start_configuration`; serverbound
  `intention`, `login_acknowledged`, configuration `finish_configuration`,
  play `configuration_acknowledged`.
- **Inbound switches on receipt** (verified (javap), `PacketDecoder.decode`
  → `ProtocolSwapHandler.handleInboundTerminalPacket`): after decoding a
  terminal packet the decoder turns auto-read off and removes itself, and
  the listener installs the next State's decoder
  (`setupInboundProtocol`) before anything else is decoded. So every frame
  after `login_finished` is configuration, even before the client acks.
- **Outbound switches after the ack** (verified (javap),
  `ClientHandshakePacketListenerImpl.handleLoginFinished`,
  `ClientConfigurationPacketListenerImpl.handleConfigurationFinished`):
  `setupInboundProtocol(next)`, then `send(ack)`, then
  `setupOutboundProtocol(next)`. `handleLoginFinished` then sends a brand
  `custom_payload` and `client_information` (the Bot does not, yet).
- **Compression** (verified (javap), `handleCompression`): handled on the
  network thread as it is decoded, `setupCompression(threshold, false)`,
  both directions at once, so it applies from the next frame.

## Framing and compression

- **A negative threshold means no compression** (verified (javap),
  `Connection.setupCompression(int, boolean)` starts `iload_1; iflt`, and
  that branch removes the `decompress` and `compress` handlers). A
  threshold of 0 or more installs (or updates) both. The wiki's *Set
  Compression* agrees: "Negative values will disable compression".
- **Frame length** (verified (javap), `Varint21FrameDecoder.decode`): at most
  3 VarInt bytes ("length wider than 21-bit", so at most 2 097 151), and
  never 0 ("Frame length cannot be zero"). Both are `CorruptedFrameException`,
  which ends the connection. The encoder side (`Varint21LengthFieldPrepender`)
  throws when the length needs more than 3 bytes, and `CompressionEncoder`
  throws for more than 8 388 608 bytes of data ("Packet too large"), before
  deciding whether to compress.
- **Decompression** (verified (javap), `CompressionDecoder`): data-length 0
  passes the rest through. Otherwise, only with `validateDecompressed`, a
  data-length below the threshold or above `MAXIMUM_UNCOMPRESSED_LENGTH`
  (8 388 608) is a `DecoderException`. The **server** passes `true`; the
  **client** passes `false`
  (`ClientHandshakePacketListenerImpl.handleCompression` calls
  `setupCompression(threshold, false)`). Then `inflate` allocates a direct
  buffer of exactly data-length bytes (a negative one throws), inflates once
  into it, and throws unless it got exactly that many bytes. So a longer
  stream is truncated, not rejected, and nothing after the declared length
  (the rest of the stream, its Adler-32 trailer, trailing bytes) is read.
- **Bool** (the audit, `AbstractByteBuf.readBoolean`): `readByte() != 0`.
- **String** (verified (javap), `Utf8String.read`): a byte length above
  `utf8MaxBytes(n)` = 3n, or negative ("Weird string!"), throws; so does a
  decoded length above n UTF-16 units. The bytes are decoded with
  `ByteBuf.toString(UTF_8)`, which replaces malformed UTF-8.
